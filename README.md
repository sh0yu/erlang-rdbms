# tether

セッションが接続より長生きするデータベース。Erlang/OTP 25。

```
bin/tether demo     exactly-once と local-first を見せる
bin/tether bench    預かり(escrow)が効くかを測る
bin/tether test     試験一式 (87件)
bin/tether shell    対話シェル
```

## 何が違うのか

**どのデータベースも「入ったのか分からない」をアプリケーションに押し付けている。**

| | |
|---|---|
| Cassandra | `WriteTimeoutException` は「必要な数のACKが返らなかった」であって、失敗ではない。部分的に書かれたものは巻き戻らず、hinted handoff と read repair がそれを伝播させる |
| FoundationDB | `commit_unknown_result` を明示的に文書化し、冪等な設計を要求する |
| Spanner | 同様。トランザクションは原子的だが、クライアントから見た不確実性は残る |
| TigerBeetle | **解いている。** ただし複式簿記専用 |

tether は再送を吸収する。

```erlang
Ops = [{cas, {<<"accounts">>, <<"alice">>}, undefined, <<"100">>}],

{ok, [ok]} = tether:request(<<"alice">>, 1, Ops),   % 初回
{ok, [ok]} = tether:request(<<"alice">>, 1, Ops),   % 再送。実行されない
{ok, [ok]} = tether:request(<<"alice">>, 1, Ops),   % 何度でも同じ

{error, 1, {conflict, <<"100">>}} =
    tether:request(<<"alice">>, 2, Ops).            % 通番を進めれば別の要求
```

「既にあれば失敗する」操作で試すのが要点。もし再実行されていたら
2度目は `conflict` になるので、**答えの形そのもので露見する**。

応答が返る前に接続が切れても、セッションプロセスが死んでも、
ノードが落ちても、同じ通番で聞き直せば答えが分かる。

## なぜ BEAM なのか

再送を吸収するには、クライアントごとの記憶が要る。既存のアーキテクチャでは
置き場所が2つしかない。

* **行にする** — 動く(冪等キーの表)。しかし行は何もできない。オフライン中に
  溜まった操作の統合も、復帰時の差分押し出しも、自己失効もできない。
  そして何より、アプリケーションの規律であってデータベースの機能ではない
* **スレッドにする** — 振る舞いを持てるが、1本あたり数十KB〜数MB。数が載らない

BEAM のプロセスは**生きていて、かつ安い**。実測:

```
約 3.3 KB / セッション、生成 20〜28 µs
→ 100万セッションで約 3.1 GB。1台に載る
```

軽量な並行実体を大量に持てるだけなら Go の goroutine や .NET Orleans もできる。
BEAM が唯一なのは、それに加えて

* **ヒープがプロセスごとに独立** — GCが他を止めない。1人が p99 を汚染しない
* **リダクション計数による先取り** — 暴走しても他は動き続ける
* **監視がVMの原始機能** — 死ねば隔離され、次の要求で作り直される

## 構成

```
tether_rec        ログレコード形式(純粋)。切り捨てと破損を区別する
tether_log        追記ログ。group commit。500件の書き込みが fsync 1回
tether_data       データ本体(純粋)。不変値なので原子性がただで付く
tether_entry      ログに載る1件(純粋)。通し番号・要求・**返した答え**
tether_snapshot   スナップショット。ログを切り詰めるため
tether_recovery   ログ再実行。記録された答えとの一致を検査する
tether_store      状態を持つ。fsync を待たず、返答の権利をログへ委譲する
tether_session    クライアント1人につき1プロセス。再送を吸収し、
                  **圏外の間の変更を溜め、差分として渡す**
tether_escrow     数値の下限を協調なしで守る(純粋)
tether_replica    クライアント側の複製(純粋)。**サーバと同じ関数で状態を作る**
tether_client     端末の口。圏外で読み書きし、復帰したら送る
tether_sessions   ETS名簿と購読の配布。引くのにプロセスを経由しない
```

永続化されているのはログだけで、データはメモリにある。だから復旧は
ログの再実行で済み、ARIES のような仕掛けが要らない。

## 設計上の判断

* **答えを記録する** — 復旧のためだけなら操作で足りるが、それでは再送に
  初回と同じ答えを返せない
* **失敗した要求も記録する** — 記録しないと、再送を再実行してしまい、
  そのときの状態次第で成功しうる。それは exactly-once の破れ
* **セッションは temporary** — 自動再起動にすると、暴走するクライアントが
  再起動の嵐を起こし、supervisor の強度上限に触れて他を巻き込む
* **未応答は1件まで** — 通番 n+1 を送った時点で n の答えは届いている。
  記憶が定数サイズに収まる
* **破損したログは起動を拒否する** — 読めるところまで読んで続行すると、
  ディスクの故障が「データが少し古いだけ」に化けて表に出てこない

詳細と、作りながら分かったことは `DESIGN.md`。

## local-first — セッションがクライアントの複製を管理する

**ここが BEAM を使う理由である。**

```erlang
%% コレクションを購読する。現在の中身と版が返る
{ok, Version, Rows} = tether:subscribe(<<"alice">>, <<"orders">>),

%% --- ここから圏外。数時間でも数日でも ---
%% その間、alice のセッションプロセスはサーバで生きていて、
%% orders への変更を溜め続ける

%% 復帰。見落とした分だけが返る(全件ではない)
{delta, V, Changes} = tether:sync(<<"alice">>),

%% 溜めきれなかった場合はこちら。**そのクライアントだけ**が取り直す
{resync, V, [{<<"orders">>, AllRows}]} = tether:sync(<<"alice">>).
```

これが行にはできない。行は溜められない。接続に紐づける設計でもできない
(切れたら消える)。スレッドでは 10^6 クライアントぶん載らない。

**生きていて、かつ安いプロセスが要る。** 実測 約3.3KB / 生成 20µs。

そして溜めるからには上限が要る。無制限に溜めると、戻ってこない
クライアント1人がメモリを食い潰す。PostgreSQL の論理レプリケーション
スロットが WAL を溜め続けてディスクを埋める事故と同じ形で、あちらは
スロット単位で止められない。ここは**プロセス単位に上限がある**ので、
溢れたクライアントだけが「取り直し」に落ちる。

```
2000購読者への配布           10ms (5µs/購読者)
購読していないコレクション   届かない
内部用の鍵($pool 等)         外に出ない
```

## 端末側 — 圏外で読み書きする

```erlang
{ok, C} = tether_client:open(<<"alice">>, <<"orders">>),

ok = tether_client:offline(C),                      %% 本当に通信を止める

{ok, <<"a">>} = tether_client:read(C, {<<"orders">>, <<"o1">>}),   %% 手元から
{ok, [ok]}    = tether_client:write(C, [{put, K, V}]),             %% 積まれる
{ok, <<"v">>} = tether_client:read(C, K),                          %% 自分の書き込みが見える

ok = tether_client:online(C),
{ok, #{accepted := N, rejected := R, unsent := U}} = tether_client:sync(C).
```

手元の見え方は `tether_data:apply_batch/3` で計算する。**サーバが使うのと
まったく同じ純粋関数**なので、意味がずれない。

圏外の書き込みには2種類ある。

| | |
|---|---|
| **楽観的** | `put` / `cas` / `delete`。サーバが拒めば覆る |
| **確定的** | 預かりの範囲内の `consume`。**覆らない** |

同期エンジンは全部を楽観的に扱うので、圏外で見せた結果が後で覆る。
預かりがあると、覆らないと断言できる範囲が生まれる。

## 圏外で「書く」ときの問題 — 預かり(escrow)

読むだけなら差分で足りる。書くと、**共有された有限資源**が問題になる。

既存の同期エンジン(ElectricSQL, PowerSync, Replicache)も CRDT も、
オフラインの書き込みは受け付けるが**下限を守れない**。CRDTカウンタで
「10から1引く」と「10から7引く」を統合すれば 2 になり、在庫が3しか
無くても8個売れる。

預かりは、協調が要るのが「在庫が尽きるとき」だけであることを使う。

```erlang
%% オンラインのうちに持ち分を預かる
{ok, [{granted, N, Expires}]} =
    tether:request(<<"alice">>, 1, [{acquire, <<"sku:1">>, 5, 600000}]),

%% --- 圏外。中央が空になっても、この範囲なら売れる ---

%% 戻ってから、積んだ操作をまとめて流す。**最初の失敗で止まる**
{ok, Results} = tether:request_batch(<<"alice">>, 2,
    [[{consume, <<"sku:1">>, 1}, {put, {<<"orders">>, <<"o1">>}, <<"c">>}],
     [{consume, <<"sku:1">>, 1}, {put, {<<"orders">>, <<"o2">>}, <<"c">>}]]),

%% 端末を作り直したら、自分の位置と権利を聞き直せる
#{last_seq := L, grants := G} = tether:resume(<<"alice">>).
```

配る量は TCP の輻輳窓と同じ形で自動調整する。

```
使い切るたびの配布量        [4, 8, 16, 32, 64, 128]
枯渇に向かう配布量          [4, 4, 3, 1, 1, ..., sold_out]

20000件の売上のうち、接続が要ったのは 1000回 (5%)
遊休(配ってあるが未使用)は 19%
```

**escrow は速くするための機構ではない**(原子的減算に対しては 0.6〜0.9倍)。
**接続を不要にするための機構**である。そして escrow 自体は BEAM を
使っていない — plpgsql でも書ける。BEAM が要るのは上の購読の方である。
正直な計測と限界は `DESIGN.md`。

## まだ無いもの

* **ストアが単一の直列点。** セッションは並列だが、適用は直列
* レプリケーションが無い。1ノードのみ
* 問い合わせは鍵による読み書きのみ。走査も索引も無い
* 認証・認可が無い。resume も sync も、誰でも他人のものを読める
* 購読はコレクション単位のみ。述語による絞り込みが無い
* クライアント側の永続化が無い(プロセスが死ぬと手元の複製が消える)
* 購読の解除でクライアント側の複製を捨てる処理が無い
